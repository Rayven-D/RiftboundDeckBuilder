# Brief H-140 / H-125 / H-108: after Send link, closing, and the other-device confirm

**Problem.** In `SignInDialog` (`web/src/app/core/sync/sync-dialogs.ts`), a successful send shows "Check your email
for a sign-in link." with no address and no way forward (#6). Once, Escape after a failed send left focus on `<body>`
(#22). A link opened on another device asks with native `prompt()` (`completeEmailLink`, `sync.service.ts`) (#7).
All strings below are SYNC-006 / SYNC-005 text, written exactly. The one new string is the H-108 title (decision 12).

## Decisions: H-140 sent state
1. **Markup, top to bottom, replacing the form:** `<p class="sent-line" role="status" tabindex="-1">` holding
   "We sent a sign-in link to <strong>{address}</strong>. Open it on this device to finish signing in." Then
   `<p class="note">Didn't get it? Check your spam folder.</p>`, then `<div class="sent-actions">` with the two buttons,
   then the failure slot. Why: one block that reads in the order you act on it, with the address as the thing you check.
2. **Address emphasis:** `<strong>` (weight 600, same colour) with `overflow-wrap: anywhere`. Why: a typo is easiest to
   spot when the address stands out, and long addresses must wrap at 375 and not push the dialog sideways.
3. **Focus after a successful Send link → the sent line** (`afterNextRender`, the H-104 `focusEmail` pattern), with
   `outline: none` on it because it isn't a control. Why: the focused Send link is destroyed with the form, so without a
   move focus drops to `<body>`. Focusing the line makes a screen reader read the whole sentence, address included.
   A brand-new live region's first text isn't announced reliably, so `role="status"` is for the next change only.
4. **Send again keeps focus.** `disabledInteractive` on **both** text buttons. `sending()` disables both, and
   Send again's label reads `Sending…` (U+2026). Give it a `min-width` so the label swap doesn't change its width.
   On success the line text changes in place to "We sent a new sign-in link to **{address}**. …", and the
   persistent `role="status"` announces it (polite). Focus stays on Send again. Why: a natively disabled focused
   button drops focus to body, which is the same bug H-106 fixed.
5. **"new" wording:** a `resent` flag set by a successful Send again and reset by Use a different email. A Send link
   from the form always shows the plain "We sent a sign-in link to…". Why: "new" only makes sense for the same address.
6. **Failure in the sent state:** the sent line keeps its last text, and the failure slot shows the existing
   `.error` pattern (`<app-icon name="error" />` + `SEND_LINK_FAILED`, `--color-danger`, `--font-size-sm`, icon on
   line 1). Accessibility without a field: the slot is a persistent `<div role="status">` (always rendered in the
   sent state, empty until a failure) so adding the line is announced, and Send again gets
   `aria-describedby` → the line's id while it shows (reuse `errorId`), so going back to the button re-reads it. Not
   `role="alert"`, because the user just pressed the button and is waiting for an answer, so polite is enough. The
   line clears when Send again is pressed and on Use a different email. Why: same look as the form failure, and
   it is announced once.
7. **Use a different email:** `sent=false`, `resent=false`, error cleared. The form shows with `email()` in the field
   (keep `[value]="email()"`) and `focusEmail()`. Send link is enabled because the value has an '@'. The stored address
   doesn't change (the engine only stores on success). **Reopen → form:** already true, because `sent` is per instance. Keep it.
8. **Buttons in content, not in `mat-dialog-actions`.** `.sent-actions { display: flex; flex-wrap: wrap;
   gap: var(--space-2); margin-inline-start: calc(-1 * var(--space-3)); padding-bottom: var(--space-1); }`: plain
   `matButton` (text) buttons, start-aligned, with the row pulled left by the text button's 12px padding so the
   labels line up with the paragraphs. Why: they act on the message above them. Next to Close they would read as
   dialog-level choices, and Close must stay the only action-row button. Check: the left focus ring (2px + 2px offset)
   still has ≥ 8px before the content edge.
9. **Spam line:** reuse `.note` (`--color-text-muted`, body size), no icon. Why: it's a hint, not a status, and the
   muted colour puts it under the main line. Contrast: muted on the dialog surface must measure ≥ 4.5:1 in both themes.
10. **Phone (≤ 40rem):** `.sent-actions { flex-direction: column; align-items: flex-start; gap: 0; }`. The 48px
    touch targets give the spacing. Send again comes first, then Use a different email. They aren't full width
    (they're text buttons). Why: at 280px of content width the two labels plus the gap don't fit on one line, and
    ragged wrapping looks broken. **Don't regress H-139 / H-124:** the form's `.email` padding-bottom and the
    375 Send link ring (0 px spare below) are untouched by this change. The sent block keeps its own
    `padding-bottom: var(--space-1)` so the last button's ring isn't clipped. Remove the last `<p>`'s bottom margin
    if needed, so there is no scrollbar.

## Decisions: H-125 focus restore
11. **Pass the trigger, then use a fallback.** `openSignIn(trigger?: HTMLElement)`. The header button passes
    `$event.currentTarget`, and the panel does the same through `gate.signIn(trigger)` → `actions.signIn(trigger)`.
    `dialog.open(..., { restoreFocus: trigger ?? true })`. After `afterClosed()`: if `document.activeElement` is
    `body` or `null` and `trigger?.isConnected`, call `trigger.focus()`. If the trigger is gone (the panel
    re-rendered), focus `#main` (it already has `tabindex="-1"`). Never move focus if it's already on a real
    element. Why: Material restores only what was focused at open, and Safari doesn't focus a button on click, so
    an explicit trigger plus one guarded fallback covers both. A likely cause of #22 is that the focused element
    is destroyed inside the dialog (old natively disabled Send link, and now the form swap). Decisions 3 and 4
    remove that cause, and this decision covers what remains.

## Decisions: H-108 other-device confirm (`ConfirmEmailDialog` in `sync-dialogs.ts`)
12. **Content:** title `Finish signing in` (new string, an `<h2 mat-dialog-title>`). Body `<p>`: "Confirm your
    email address to finish signing in." (exact). Then one outline `Email address` field (`type="email"`,
    `autocomplete="email"`, `hideRequiredMarker`, full width). Actions `align="end"`: **Cancel** (text), then
    **Finish sign-in** (filled), the sign-out dialog's order. No intro and no providers. Why: the sign-in dialog's
    style, smaller.
13. **Behaviour:** `autoFocus: 'first-tabbable'` puts focus in the field. It's a `<form novalidate>`, so Enter
    submits. Finish sign-in is `[disabled]` until the trimmed value includes '@' (plain `disabled` is fine, because
    focus is in the field whenever that state changes). Submit closes with the trimmed address. Cancel, Escape and
    backdrop close with `undefined`, so no sign-in and no message (SYNC-005 cancel). The service reads
    `stored ?? await confirmEmail()` and returns on empty. A failed or expired link still shows the engine's
    SYNC-005 text after the dialog closes.
14. **Focus after close at start-up:** `restoreFocus: false`, and leave focus where it lands (the document start).
    Why: there's no trigger, and the next Tab reaching the Skip to content link is the right first stop on a fresh
    load. Jumping to `#main` would skip it.

**Out of scope:** return path and "You're signed in." (H-145), Google flow, any cooldown. **Must keep:** H-104 form
layout, the H-106 failure behaviour, H-139 rings, and only one filled button per dialog.
