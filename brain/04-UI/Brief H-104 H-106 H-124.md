# Brief H-104 / H-106 / H-124: the sign-in dialog leads with the email field

**Problem.** In `SignInDialog` (`web/src/app/core/sync/sync-dialogs.ts`), launch users must click "Sign in with
an email link" to see the field. Focus stays on that button, and it stays filled next to a second filled Send link
(`signin-email-1440-dark.png`). A failed send shows the SYNC-005 sign-in text in muted grey, with no icon and no
invalid state, and there's no "Sending…" (`signin-error-1440-dark.png`). At 375 the content scrolls by 4px and the
field and button sit at half width (`signin-email-375-dark.png`).

## Decisions
1. **(a) Email link only (launch):** render **no** `.providers` div at all. An empty div still adds its
   `--space-3` margins. The form comes straight after the intro (and after the offline note when it shows).
   Focus goes in the field on open. `autoFocus: 'first-tabbable'` (`sync.service.ts`) already lands there because
   the input is the first tabbable element. Keep that, and don't add a second focus mechanism. Opening still loads no `firebase` (SYNC-002).
2. **(b) 2+ providers: every provider button is outlined from the start** (drop `first ? 'filled'`). Why: the
   providers are equal choices, not a recommended one plus extras. Send link is then the dialog's only filled
   button with no restyle. A filled button turning outlined while you look at it would read as "something
   changed state", which it didn't. "Continue with Google" still closes the dialog at once, so an outlined button
   is fine for it. The email-link button stays visible after the reveal. Pressing it again just refocuses the
   field: it is not a toggle, so no `aria-expanded`. After the reveal, focus moves to the input once it has
   rendered (after the `@if` renders, e.g. a `viewChild` + `afterNextRender`).
3. **Send-failure message: a custom line, not `mat-error`.** The field has no `FormControl`, so `mat-error`
   would need error-state plumbing. Its colour also comes from Material's generated palette, not `--color-danger`.
   Reuse the import dialog's pattern (`import-dialog.scss` `.error`): `<p class="error" id="send-error">`
   with `<app-icon name="error" />` + `MESSAGES`-style constant text, exactly
   "Couldn't send the link. Check the address and your connection, then try again." It **replaces**
   `MESSAGES.signInFailed` here (SYNC-005 text never shows for a send). Style: `color: var(--color-danger)`,
   `font-size: var(--font-size-sm)`, `display: flex; align-items: flex-start; gap: var(--space-1)`. It sits under
   the field row, spanning the full width, with `margin-top: var(--space-2)`. `flex-start` keeps the icon on the
   first line when the text wraps at 375. Contrast is `--color-danger` on the dialog surface (H-102 measured 7.44 / 6.53 on `--color-bg`,
   6.51 / 7.07 on `--color-surface`). The check measures the real surface.
4. **Invalid field.** While the error shows, the input has `aria-invalid="true"` and `aria-describedby="send-error"`.
   With no error, `aria-describedby` is removed; `aria-invalid` is owned by MatInput (absent when empty, `"false"` on a filled field, see run 2). Add the class `send-failed` on the `mat-form-field`
   and, in `styles.scss` next to H-102's danger rules, `.mat-mdc-form-field.send-failed { @include
   mat.form-field-overrides((outlined-outline-color, outlined-hover-outline-color,
   outlined-focus-outline-color: var(--color-danger))); }`. The red outline is extra. The icon and text carry the
   meaning (never colour alone).
5. **Not `role="alert"`. Focus does the announcing.** On failure, move focus to the input. A screen reader then
   reads "Email address, invalid, rj@example.com, Couldn't send the link…" once. An alert as well would
   announce it twice. Moving focus also stops the next point from dropping focus to `<body>`
   (probably the cause of review #22).
6. **Sending.** The label reads `Sending…` (U+2026) while `sending()`. Use **`disabledInteractive`** on Send link
   so it keeps focus while disabled (`aria-disabled`, clicks ignored, and `send()` already guards with `sending()`). A
   natively disabled focused button drops focus to `<body>`. Give the button `min-width` so the label swap doesn't
   change its width on desktop. The field keeps the address after a failure (nothing cleared, nothing stored).
7. **When the error clears:** on the first edit of the field (`input` event), and when Send link is pressed
   (as now: `error.set(null)` at the start of `send`). Not on blur, and not on a timer.
8. **Layout and breakpoint.** Use the app's phone query `@media (max-width: 40rem)` (as in `styles.scss`).
   - **Desktop/tablet:** `.email` stays `display: flex; flex-wrap: wrap; align-items: center; gap: var(--space-2)`.
     The field gets `flex: 1 1 16rem` so it fills the row, and Send link sits on the right at its own width. The error line gets `flex-basis: 100%`.
   - **≤ 40rem:** `.email { flex-direction: column; align-items: stretch; }`, so the field is full width with Send
     link **full width** below it (gap `var(--space-3)`). A full-width primary is easy to reach with a thumb and
     reads as the dialog's one action. Right-aligned would look like a second dialog-actions row next to Close.
   - Keep H-139's `padding-bottom: var(--space-1)` on `.email`. **No scrollbar:** `.mat-mdc-dialog-content`
     `scrollHeight === clientHeight` at 375 and 1440. Likely sources are the empty `.providers` margins and the last
     `<p>` margin. Fix by removing the extra spacing, never with `overflow: hidden`.
   - Optional, cheap: `hideRequiredMarker` on this one field (the `*` is noise; `required` stays for AT).

Sign in to import your cards … sign in on.      Sign in to import your cards

**Out of scope:** sent state (H-140; success still swaps the form for today's line), focus restore on close (H-125),
other-device confirm (H-108). **Must keep:** H-139 focus ring (Send link ring not clipped, 2px outside), H-101
snack-bar offset, and H-102 `danger` stays off this dialog (Send link is the accent filled button).

## Accept (ui-engineer Playwright pass)
At **1440 and 375, dark and light**, default config, plus `['email-link','google']` via the environment:
- (a) Open from the header and from a gate panel: no provider button; `document.activeElement` is the email input;
  network shows no `firebase` chunk. Exactly one `matButton="filled"` in the dialog.
- (b) Both provider buttons outlined, no field. Enter/Space on "Sign in with an email link" puts focus on the
  input. Send link is the only filled button.
- Tab order (a): input → Send link → Close. (b): email-link → Google → input → Send link → Close. Shift+Tab reverses it. Escape closes.
- Sending (stalled request): the label reads "Sending…", `aria-disabled="true"`, focus still on the button, the button is the same width.
- Failure (emulator network error): the exact text with the icon under the field. No "Sign-in didn't complete…". Focus is on
  the input, which has `aria-invalid="true"` and `aria-describedby` → the message's id. The accessibility snapshot shows the description.
  The field still holds the address, the outline is `--color-danger`, and text contrast is ≥ 4.5:1. Typing one character clears the message and both aria attributes.
- 375: field and Send link are full width (equal widths), the error wraps with the icon on line 1, `.mat-mdc-dialog-content`
  has no scrollbar (scrollHeight = clientHeight) in the form, error and offline states, Send link is ≥ 44px tall, and
  the Tab ring on Send link is visible on all four edges.
- Reduced motion: nothing animates beyond Material defaults. The console is clean.

**Deviation from decision 4, accepted:** with no error, the input now has `aria-invalid="false"`, not no attribute,
because MatInput owns the attribute. ARIA treats "false" the same as absent, and screen readers announce nothing. This is
the price of the review's switch to Material ownership. Decision 4's "remove both attributes" still holds for `aria-describedby`.
