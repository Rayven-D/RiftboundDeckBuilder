# Brief H-245 H-246 H-247: FAB, footer, theme switch

**RJ-requested (2026-11-25). These are RJ's decisions, not proposals:**
1. The Import / Add FAB on Decks and Collection must **never** overlap the footer.
2. The footer is much too thick: make it slim; keep what is legally needed.
3. Theme moves out of the footer (and the account menu) to a **light ↔ dark switch next to Sign in / the account
   control** in the header. **No System option.** A stored choice wins; only with nothing stored does the app use the
   OS `prefers-color-scheme`. Toggling stores the choice. Old stored "system" values count as nothing stored.
4. (Added by RJ the same day, folded into H-246.) **Phones only:** sign-in / account moves out of the header into the
   bottom tab bar, bottom right after Tournaments: a person icon labelled "Sign in" when signed out, the letter avatar
   when signed in. Desktop keeps the header control.

Three build items, one per change. Do them in the order H-245 → H-246 → H-247 (H-246 and H-247 both edit
`app.html` / `app.scss`; H-247 assumes the theme switch has already left the footer).

## Root cause of the FAB overlap

The FAB is `position: fixed` (bottom `--space-5`, or above the tab bar on phones), so it never moves. H-176 (from my
own [[Brief H-175]] F4) protected the footer by adding `html.has-fab app-root { padding-bottom: var(--fab-clearance) }`,
an empty band **below the footer**. That only guarantees clearance at the **exact scroll end**. While the last
~footer-height of the page scrolls past, the footer travels up through the bottom of the viewport and passes **under**
the fixed button. The thicker the footer (177 px on phones, the theme toggles wrap onto their own row) and the
shorter the viewport (landscape phones, 1024 × 768), the longer the window and the more text is covered. Side effect:
the reserve leaves an odd empty strip under the footer on every FAB page, and on short pages the footer sits 92 px
above the window bottom with the FAB floating under it.

Safe-area is not the cause (the FAB and tab bar already add `env(safe-area-inset-bottom)`); the phone case is the same
mechanism made worse by the taller footer.

## H-245: the FAB docks above the footer

**Decision:** keep the FAB fixed at its rest position, and **dock** it: when the footer's top edge comes within reach,
the FAB moves up with the footer so its bottom stays exactly `--space-4` (16 px) above the footer's top border. The
space it needs is reserved **above** the footer (inside `<main>`), not below it.

Why this over the alternatives:
- *`position: sticky` at the end of the page:* parks naturally with no script, but sticky can only move an element up
  from its place in the flow. The FAB is deliberately early in the DOM (Tab order, COLL-094 / F7), so it would need a
  flex `order` trick on every page host, and on a short page (Decks with 3 decks) it would sit right under the content
  mid-screen instead of bottom right unless `main` and every page host became flex columns. Too much layout churn.
- *Hide the FAB when the footer shows:* the main action would vanish at the end of the list, exactly where users
  finish scrolling. No.
- *Keep reserving space below the footer:* that is today's bug.

### D1. Position and docking (all widths)
- Rest position unchanged (COLL-094 a / [[Brief H-175]] F2): ≥ 40rem `bottom: var(--space-5)` on the content edge;
  < 40rem above the tab bar (`--tabbar-height + --tabbar-border + env(safe-area-inset-bottom) + --space-4`).
- New: a dock offset `--fab-dock` (px, ≥ 0). With `restBottom` = the FAB's rest bottom edge in viewport px
  (`innerHeight − rest offset`) and `footerTop` = `.site-footer` `getBoundingClientRect().top`:
  `dock = max(0, restBottom − (footerTop − 16))`. Applied with the **individual `translate` property**:
  `translate: 0 calc(-1 * var(--fab-dock, 0px))`. Keep `transform` for the hover lift and press scale (they keep their
  `--dur-fast` transition); **`translate` has no transition**, so the button tracks the footer 1:1 and never lags.
- Set `--fab-dock` on `document.documentElement` (not the button), so snack bars can use it too (D3).
- When to compute: in the existing `window:scroll` handler and on `resize`, throttled to one `requestAnimationFrame`;
  only do the rect read while the footer is near the viewport (an `IntersectionObserver` on `.site-footer` with
  `rootMargin: '0px 0px 120px 0px'` flips a flag; when it is not intersecting, `--fab-dock` is `0px`). Also a
  `ResizeObserver` on the footer (its height changes when text wraps). Remove the property on destroy along with
  `has-fab`.
- Reduced motion: nothing to change; docking is position tracking, not animation.

### D2. Reserve space above the footer, not below
- Remove `html.has-fab app-root { padding-bottom: var(--fab-clearance) }`. The phone tab-bar reserve on `:host`
  in `app.scss` stays (the footer must still end above the tab bar).
- Add `html.has-fab .site-main { padding-bottom: calc(56px + 2 * var(--space-4)) }` (88 px; `56px` is the FAB height,
  consider a `--fab-size: 56px` token used by both). Scrolled to the end, the docked FAB occupies the band between the
  last content row and the footer: content ends 88 px above the footer, the FAB spans 72 → 16 px above it, so 16 px
  clear on both sides.
- Keep `scroll-padding-bottom: var(--fab-clearance)` as is (keyboard focus clears the FAB at rest).

### D3. Snack bars follow the dock
`html.has-fab .mat-mdc-snack-bar-container { margin-bottom: calc(var(--fab-clearance) + var(--fab-dock, 0px)) }`,
so an Undo notice shown at the page end still sits above the docked FAB (H-101 / F5 rule kept).

### D4. Breakpoints
| Width | Rest | Docked (at page end, after H-247) |
|---|---|---|
| ≥ 72rem (1440) | right edge on the content edge, 24 px from the bottom | 16 px above the footer border, same right edge |
| 40–72rem (768, 1024) | `--content-gutter` from the right, 24 px from the bottom | 16 px above the footer border |
| < 40rem (375, 390, 320) | gutter from the right, 16 px above the tab bar hairline | 16 px above the footer border (the footer itself ends above the tab bar) |
| Landscape phone (≥ 40rem wide, ~360 tall) | desktop rule | docks as above; no special case needed |
| Short page (Decks with a few decks, 1024 × 768) | footer at the window bottom | FAB docked 16 px above the footer, bottom right |

### H-245 Accept
1. On `/collection` (Small and Large test data) and `/decks` (3 test decks), at 1440 × 900, 1024 × 768, 768 × 1024,
   375 × 812 and 812 × 375, scroll the last 400 px in 10 px steps (a Playwright loop like the one in this brief): at
   every step the FAB's rect does not intersect the `.site-footer` rect (strictly: FAB bottom ≤ footer top − 16 px,
   ±1 px). Phone: test with the label expanded (scroll up) and collapsed (scroll down).
2. Scrolled to the very end: the last tile row / deck row is fully above the FAB, the FAB is fully above the footer,

3. While the footer is off screen the FAB is at exactly the rest position of COLL-094 (a) (no drift).
4. After a collection import commit at the page end, the Undo snack bar is fully above the docked FAB at 1024 and 375.
5. Hover lift and press still animate; the docking does not lag the scroll (no `transition` on `translate`).
6. Keyboard: Tab order unchanged (header → FAB → toolbar → grid); a tile focused by arrow keys at the bottom of the

7. Unit test: the dock formula (footer far below → 0; footer top at `restBottom` → 16; footer higher → grows 1:1).

## H-246: light/dark switch in the header

### T1. Behaviour (replaces SYNC-157 a and SYNC-158; spec text H-244)
- **Values stored:** `light` or `dark` under the existing key **`device-theme`** (unchanged: outside `rift.`, never
  synced, survives sign-out and account deletion, SYNC-157 b, c).
- **Effective theme:** the stored value if it is `light` or `dark`; otherwise (nothing stored, `system`, or anything
  unknown) the OS setting, `matchMedia('(prefers-color-scheme: light)').matches ? 'light' : 'dark'`.
- **Nothing stored and the OS setting changes while the app is open:** the app follows it live (the stylesheet
  already does) and the switch's state updates with it (a `matchMedia` change listener). Once the user toggles, the
  stored value wins and OS changes are ignored.
- **Toggling** sets the opposite of the effective theme, applies it at once (no animation of the page colours,
  SYNC-157 d), and stores it. There is no way back to "follow the OS" in the UI (RJ: no System option).
- **Migration:** any stored value other than `light` / `dark` (a stray `system`, junk) is treated as nothing stored.
  Today's code never writes `system` (System removes the key), so in practice nothing needs rewriting; on read,
  remove an unknown value (`removeItem`) so storage stays clean. No notice.
- **No flash:** the inline script in `index.html` is already correct (applies only `light` / `dark`; with no
  attribute the CSS media query decides). Keep it; keep `theme.ts`'s comment in step.
- `theme-color` meta tags and `color-scheme` on `html`: as today for an explicit choice.
- Cross-tab: keep the `storage` listener.

### T2. The control
**An icon toggle button** (not a sliding switch, not a menu): it is one binary action, a slider would add a second
visual metaphor to a calm header and needs more width on phones.

| Property | Value |
|---|---|
| Element | native `<button type="button">` (new `app-theme-toggle`, replaces `app-theme-switch`) |
| Accessible name | **"Dark theme"** (fixed; never changes) |
| State | `aria-pressed="true"` when the effective theme is dark, `"false"` when light |
| Icon | the **current** theme: `dark_mode` (moon) when dark, `light_mode` (sun) when light; 22 px, `aria-hidden="true"`. Add both Material Symbols paths to `shared/icon.ts` in the set's existing style |
| Tooltip | `matTooltip`: **"Switch to light theme"** when dark, **"Switch to dark theme"** when light; `matTooltipShowDelay` 300 ms; position below. It is a description, not the name |
| Size | 44 × 44 px hit area, icon centred; `border-radius: var(--radius-md)`; no border |
| Colour | rest `--color-text-muted` (6.48:1 dark, 5.91:1 light on `--color-bg`); hover `--color-text` on `--color-surface-raised` (same as the account trigger's hover); pressed state is **not** shown by fill (the icon carries it) |
| Focus | the global ring (H-139: 2 px `--color-focus`, 2 px offset); focus stays on the button after toggling |
| Keyboard | Tab stop; Enter and Space toggle (native button) |
| Motion | the icon swaps with a 120 ms (`--dur-fast`, `--ease-out`) fade + 30° rotate; under reduced motion it swaps instantly. The page colours never transition |
| Loads | no Firebase, no request; renders immediately (**not** inside the `@defer` of the account menu), so the header does not shift when the account control arrives |

### T3. Placement
```
≥ 40rem  [Rift Builder]  Decks  Collection  Tournaments ............ [☾] [(R) RJ Tester ▾]
                                                                    [☾] [ Sign in ]
< 40rem  [Rift Builder] ........................................... [☾]
         (the account moves to the bottom tab bar, see "Part B" below)
```
- In `app.html`, inside `.header-row`, **immediately before** the `@defer` block, so DOM / Tab order is wordmark →
  tabs → theme → account. Gap to the account control: `--space-2` (8 px; the row's column gap of `--space-5` is too
  wide for a pair: wrap the toggle and account control in one `.header-actions` flex group with `gap: var(--space-2)`,
  or set a negative margin; builder's choice, the visual gap must be 8 px).
- Signed out, the toggle sits left of **Sign in**; while the account control is still loading the toggle already sits
  at its final place (reserve nothing extra).
- **Phones (< 40rem), RJ decision 2026-11-25: the toggle sits in the header's top-right corner, where the account
  control was.** Same 44 × 44 button, 22 px icon, same states as desktop. Alignment: pushed right by the wordmark's
  `margin-right: auto` (as the account control is today); its right edge on `--content-gutter` (16 px, or the safe-area
  inset if larger), so the icon's visual edge sits ~11 px further in, like the old account trigger's padding; vertically
  centred in the phone header row (`--header-height` 3.5rem / 56 px, so 6 px above and below the 44 px hit area).
  `flex: none`; nothing else in that corner. Tooltip below the button (it must not cover the tab bar). Reasons this
  works: (1) signed out there is no menu (the tab
  opens the sign-in dialog), and RJ wants the theme for everyone; (2) one tap, same control, same place relative to the
  page on every width; (3) the phone header would otherwise hold only the wordmark, so it has the room; (4) the tab
  bar is navigation plus account, and a theme toggle there would be the odd one out (not a destination) and squeeze
  four tabs into five at 320 px.

### T4. Remove the other theme controls
- Remove the footer `app-theme-switch` (and the component, its styles and `THEME_CHOICES` once unused).
- Remove the **Theme group from the account menu** (SYNC-151 item 6): one control, one place. The menu keeps exactly
  3 dividers: [identity, status] / [Sync now] / [Account Information, Privacy notice, What's new] / [Sign out]
  (spec-writer confirms the divider rule in H-244).
- `ThemeChoice` becomes `'light' | 'dark'`; `parseTheme` returns `null` for anything else; `ThemeService` exposes the
  **effective** theme as a signal and a `toggle()`.
